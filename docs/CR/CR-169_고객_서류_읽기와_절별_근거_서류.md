## 1. 실측 (2026-10-24 소스)

### 1.1 제안서 작성 흐름

- 생성 단계(GENERATING) 진입 때 서버가 문서 종류마다 설계, 절 작성(절마다), 조립 워크플로우를 차례로 부른다(`AIWorkflowService.java:82-142`)
- 설계 입력은 공고 본문, 공고문 요약, 요구서류, 공고 내용, 평가 항목 구조, 컴플라이언스 매트릭스다(`ProposalMcpTool.java:202-230`). 절 작성 입력은 절 범위, 대응 REQ ID 원문, 참조 샘플이다(`ProposalMcpTool.java:299-330`). 절 검증 입력은 절 본문, 공고 본문, 참조 샘플이다(`ProposalMcpTool.java:355-386`)
- 고객 서류는 셋 어디에도 들어가지 않는다. 고객 서류가 들어가는 곳은 관리자 "문서 재생성" 단추가 타는 옛 단일 문서 생성 경로(`build3PipelineContext`, `AIWorkflowService.java:341-377`)뿐이고, 그것도 파일 이름, 분류, 저장 주소뿐이다
- T1-1 BID-DOC-001 은 입력에 사용자 제출 서류(ClientDocument)를 적고 있으나 지금 흐름과 다르다
- 절 검증(CR-031)은 절 본문을 공고와 참조 샘플에 대조해 근거 없는 말을 지어낸 말로 세고, 실패하면 한 번 다시 쓴다(`AIWorkflowService.java` verifySectionWithRetry). 회사 사실을 근거 없이 넣으면 이 검증에 걸린다

### 1.2 고객 서류 자리

- 공고별 서류: `client_documents`(입찰 건에 묶임). 요구 항목과의 연결은 `requirement_fulfillment_maps`(fulfillment_type CLIENT_DOCUMENT)
- 공통 서류함: `member_documents`(회원에 묶임, 만료일 있음). 서류함에서 공고별로 넣으면 파일 바이트를 복사해 공고별 서류 한 건을 만든다(`PreCheckService.java:346`)
- 파일은 서버 저장소(StorageService)에 있다. 내용 해시는 어느 표에도 없다

### 1.3 분석 단계

- 분석(ANALYZING) 진입 때 AI 작업은 없고(CR-141), 생성 단계로는 관리자가 전환한다(`BidFSMService.java:236-245`)

### 1.4 Aimbase (소스는 고치지 않는다)

- LARGE_INPUT 단계는 PDF 와 텍스트만 받는다(Aimbase `largeinput/PdfSourceLoader`, `TextSourceLoader`). 공고 분석 v3 은 글자가 없는 쪽(도면, 스캔)을 쪽 그림으로 보고 읽게 지시한다(`docs/workflows/opportunity-analysis.steps.v3.json` extract_facts)

## 2. 설계

### 2.1 흐름

1. 관리자가 입찰 건을 분석 단계로 전환하면(DOCS_RECEIVED 에서 ANALYZING) 서버가 고객 서류 읽기를 비동기로 시작한다
2. 읽을 후보는 그 건의 공고별 서류와 그 회원의 공통 서류함 서류다. 서류함 서류 가운데 만료일이 지난 것은 뺀다. 내용 해시(SHA-256)가 같은 파일은 한 후보로 묶는다(BIZ-085)
3. 같은 내용을 이미 읽었으면 다시 읽지 않고 그 결과를 쓴다(BIZ-085). 관리자가 다시 읽기를 고를 때만 다시 읽는다
4. 읽은 결과는 서류마다 사실 목록이다. 사실 하나 = 분류, 항목, 값, 쪽, 원문 구절, 확신도, 읽은 방법(글자 또는 글자 인식)
5. 분석에서 생성으로 전환하려면 후보 가운데 읽는 중인 서류가 없어야 한다(BIZ-087)
6. 생성 단계의 설계는 공고 필요서류, 매트릭스, 후보 서류 목록(무엇을 충족하는 서류인지, 사실 요약)을 보고 절마다 근거 서류를 고른다(BIZ-088). 사람이 고르지 않는다
7. 절 작성은 그 절 근거 서류의 사실 전부를 받고, 회사 사실은 거기서만 쓴다(BIZ-089)
8. 절 검증은 같은 사실을 받아, 근거에 없는 회사 사실을 지어낸 말로 센다(BIZ-089)

### 2.2 읽을 수 있는 꼴로 내주기 (입찰대행 서버)

Aimbase 가 읽는 꼴은 PDF, 텍스트, HWP 셋으로 맞춘다. 서버가 파일 형식을 보고 정한다.

| 원본 | 읽는 꼴(read_as) | 내려받기가 주는 것 | 읽는 방법 |
|---|---|---|---|
| PDF | PDF | 원본 그대로 | LARGE_INPUT. 글자가 없는 쪽은 쪽 그림을 보고 글자를 인식한다 |
| 그림 JPG, PNG, GIF, BMP, TIFF | PDF | 그림 한 장을 한 쪽 PDF 로 감싼 것(iText) | 위와 같다 |
| DOCX, XLSX, PPTX | TEXT | 글자만 뽑은 UTF-8 텍스트(Apache POI). 표는 줄마다 칸을 탭으로 | LARGE_INPUT 텍스트 |
| TXT, CSV, MD | TEXT | 원본 그대로 | LARGE_INPUT 텍스트 |
| HWP, HWPX | HWP | 원본 그대로 | 스킬 `scripts/convert_hwp.py` 를 skill_run 으로 돌려 MD 로 바꾼 뒤 LARGE_INPUT 텍스트 |
| 그 밖(DOC, XLS, PPT, ZIP 등) | NONE | 주지 않음 | 읽지 않고 "읽을 수 없는 형식" 으로 둔다 |

형식은 확장자로 정하고, 확장자가 없으면 content_type 으로 정한다. DOC, XLS, PPT 같은 옛 형식은 서버에 그 형식을 읽는 라이브러리가 없어 읽지 않는다.

내려받기 주소는 `/mcp/document-readings/{readingId}/download` 이고, 기존 두 주소와 같은 서명(만료 시각과 HMAC)을 붙인다.

### 2.3 고객 서류 읽기 워크플로우 `client-document-read` (Aimbase, 정의는 `docs/workflows/client-document-read.steps.json`)

입력(서버가 만든다): `bidRequestId`, `files[{readingId, fileName, downloadUrl, workspacePath}]`, `hwpFiles[{readingId, workspacePath, convertedPath}]`, `targets[{readingId, targetPath}]`

| 순서 | 단계 | 종류 | 하는 일 |
|---|---|---|---|
| 1 | download_files | FOREACH(TOOL_CALL download_file) | 파일마다 `docs/{readingId}.{확장자}` 로 받는다 |
| 2 | convert_hwp | FOREACH(AGENT_CALL, 스킬 sam-proposal) | HWP 파일마다 skill_run `scripts/convert_hwp.py docs/{id}.hwp docs/{id}.txt`(내용은 마크다운, 확장자는 .txt. Aimbase 큰 문서 읽기 단계가 글은 .txt 만 받는다). HWP 가 없으면 건너뛴다 |
| 3 | extract_facts | FOREACH(LARGE_INPUT extract) | 대상마다 회사 사실을 근거와 함께 뽑는다(2.4) |
| 4 | save | TOOL_CALL save_client_document_facts | 대상별 결과를 서버에 전달한다 |

파일 하나가 실패해도 나머지는 계속한다(on_item_error continue). 워크플로우가 끝났는데 결과가 오지 않은 서류는 서버가 "읽지 못함" 으로 둔다.

### 2.4 뽑는 사실

| 분류 | 뜻 | 예 |
|---|---|---|
| COMPANY | 회사 기본 | 상호(국문, 영문), 사업자등록번호, 대표자, 주소, 설립일, CAGE, UEI |
| LICENSE | 인허가와 자격 | 인허가 종류, 번호, 발급 기관, 유효기간, 기술 자격 |
| PAST_PERFORMANCE | 수행 실적 | 사업명, 발주처, 계약 번호, 기간, 금액, 수행 내용, 역할 |
| PERSONNEL | 인력 | 직책, 인원, 자격, 경력 연수 |
| EQUIPMENT | 장비와 시설 | 장비 종류, 수량, 규격, 보유 형태, 시설 위치 |
| FINANCIAL | 재무 | 연도별 매출, 자본, 부채비율, 신용등급 |
| INSURANCE | 보험 | 보험 종류, 보상 한도, 기간 |
| CERTIFICATION | 인증 | ISO 등 인증 이름, 번호, 유효기간 |
| OTHER | 그 밖 | 위에 들지 않는 회사 사실 |

사실 하나: `{category, key, value, page, anchor, confidence(HIGH|MEDIUM|LOW), readMode(TEXT|VISION)}`. 값은 원문 말 그대로 두고, 영문 표기가 원문에 있으면 같이 적는다. 글자 인식으로 읽은 사실은 readMode VISION 이고 anchor 를 비워도 된다(BIZ-086). 추측으로 채우지 않는다.

### 2.5 저장 (입찰대행 서버)

- 새 표 `document_readings`: 내용 해시 하나에 한 줄. 읽는 꼴, 상태, 사실 목록, 사실 수, 글자 인식 사용 여부, 실패 사유, 읽은 시각
- 상태: WAITING(대기), READING(읽는 중), DONE(읽음), FAILED(읽지 못함), UNSUPPORTED(읽을 수 없는 형식)
- `client_documents`, `member_documents` 에 `content_sha256` 칸. 올릴 때와 서류함에서 복사할 때 채운다. 비어 있는 옛 줄은 읽기를 시작할 때 저장소에서 읽어 채운다
- `proposal_section` 에 `source_reading_ids` 칸(근거 서류 readingId 목록)
- 읽는 중이 워크플로우 폴링 상한(설정 간격과 횟수, 처음 값 30분, 상용은 10/25 07:21 CR-159 가 60분으로 늘림)을 넘으면 실패로 본다(BIZ-087). 서버가 재기동해 결과를 받지 못한 경우를 막는다

| GET | `/admin/bid-requests/{id}/document-readings` | 후보 서류 목록. readingId, 파일 이름, 출처, 분류, 충족하는 요구 항목, 상태, 읽는 꼴, 사실 수, 글자 인식 사용 여부, 실패 사유, 읽은 시각 |
| GET | `/admin/document-readings/{readingId}` | 사실 목록 |
| POST | `/admin/bid-requests/{id}/document-readings/run` | 다시 읽기. 몸 `{readingIds?: [], force: false}`. readingIds 가 없으면 읽음이 아닌 후보 전부. force 면 읽음도 다시 읽는다. 분석 단계에서만 된다(아니면 409) |
| GET | `/admin/bid-documents/{documentId}/sections/{sectionId}` | 응답에 `sourceDocuments[{readingId, fileName, status}]` 를 더한다 |

### 2.8 상태 전이

| 전이 | 바뀌는 것 |
|---|---|
| DOCS_RECEIVED 에서 ANALYZING | 진입 때 고객 서류 읽기를 시작한다 |
| ANALYZING 에서 GENERATING | 후보 가운데 읽는 중(폴링 상한 안)인 서류가 있으면 409 `DOCUMENT_READING_IN_PROGRESS`. 읽지 못함과 읽을 수 없는 형식은 막지 않는다 |

상태와 전이 목록은 그대로다. 수주 전략 승인 관문은 CR-171 이 같은 전이에 더한다.

### 2.9 워크플로우 지시문 (Aimbase 에 올리는 정의만 바꾼다)

- 제안서 설계(proposal-design): 절마다 sourceReadingIds 를 고르게 한다. 근거: 공고 필요서류(requiredDocuments), 매트릭스의 고객 제출 줄(fulfillmentParty CLIENT_UPLOAD), 서류의 fulfills, 평가 항목. 수행 실적 항목에는 실적 사실이 있는 서류, 기술 항목에는 인허가, 인력, 장비 사실이 있는 서류를 건다. 스킬 05 의 "구체적 사례·실적 연결" 을 붙인다
- 절 작성(proposal-write-section): 회사 사실은 sourceDocuments 의 사실에서만 쓴다. 근거가 없으면 `[Client data required: 무엇]` 자리표시를 쓴다(표시 꼴은 용어표대로 고정, 본문 언어는 지금 지시대로 한국어 초안). 스킬 00 의 F-B-P 에서 Proof 는 이 사실이다
- 절 검증(proposal-verify-fidelity): 본문의 회사 사실이 sourceDocuments 에 없으면 지어낸 말로 센다. 자리표시는 지어낸 말이 아니다

### 2.10 관리자 화면

- 입찰 상세 관리(`/bid-requests/{id}`): "고객 서류 읽기" 영역을 더한다. 후보 서류 줄마다 파일 이름, 출처(공고별 서류, 공통 서류함), 충족하는 요구 항목, 상태(읽는 중, 읽음, 읽음(글자 인식), 읽지 못함, 읽을 수 없는 형식), 사실 수. 줄을 누르면 사실 목록(분류, 항목, 값, 쪽). 분석 단계일 때 "다시 읽기" 단추. 읽는 중이면 생성 단계 전환 단추를 막고 이유를 보인다
- 제안서 Section 관리(`/documents/{id}/sections`): 우측 절 상세에 "근거 서류" 를 더한다. 파일 이름 꼬리표, 누르면 사실 목록

고객 화면은 바꾸지 않는다(BIZ-081).
