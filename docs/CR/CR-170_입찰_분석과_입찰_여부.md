## 1. 실측 (2026-10-25)

### 1.1 분석 단계

- 분석(ANALYZING)에서 갈 수 있는 상태는 문서 작성 중(GENERATING) 하나다. 종료(CLOSED)가 없다(`BidFSMService.java:87-89`)
- 분석에서 문서 작성 중 전환의 가드는 읽는 중 서류 하나다(`BidFSMService.java:168-171`, BIZ-087)
- 분석 진입 작업은 고객 서류 읽기를 줄 세우는 것뿐이다(`BidFSMService.java:249-257`). 읽기 회차는 `AIWorkflowService.readClientDocumentsAsync`(89행)가 돌리고, 워크플로우가 끝나면 결과가 오지 않은 줄을 읽지 못함으로 닫는다. 같은 내용을 다른 입찰 건이 읽는 중이면 이 건의 대상에서 제외된다(`DocumentReadingService.java:194-224`)
- 고객 서류 읽기 영역의 "분석 시작 전" 판단은 입찰 건 상태로 한다. 종료(CLOSED)는 분석 전으로 친다(`DocumentReadingService.java:69-70, 600`)
- 종료 전이에 고객 알림은 없다. 고객 알림은 관리자 검토, 제출 완료, 낙찰 셋뿐이다(`NotificationEventListener.java:171-189`)

## 2. 설계

### 2.1 흐름

1. 관리자가 입찰 건을 분석 단계로 전환하면 고객 서류 읽기가 돈다(CR-169)
2. 그 건의 후보 서류 가운데 읽는 중인 것이 없어지면 서버가 입찰 분석을 한 번 시작한다. 진입 때 이미 없으면 바로 시작한다(BIZ-090)
3. 입찰 분석 워크플로우가 세 단계로 종합 분석 리포트(스킬 01 STEP 2~7), 캡처플랜(11), Bid/No-Bid 결정(02)을 차례로 써서 서버에 저장한다
4. 서버가 Bid/No-Bid 결정의 점수와 정책값으로 Pwin, 판정, 강점과 약점, 핵심이슈 순위를 계산한다(BIZ-091)
5. 관리자가 입찰 상세 관리의 입찰 분석 영역에서 셋을 보고 Go, 조건부 Go(조건을 기재), No-Go(사유를 기재) 가운데 하나로 정한다(BIZ-092)
6. Go 나 조건부 Go 여야 문서 작성 중으로 전환된다. No-Go 면 관리자가 입찰 건을 종료한다. 분석에서 종료로 가는 전이를 추가한다
7. 관리자는 분석 단계에서 다시 분석을 선택할 수 있다. 신규 회차가 지금 분석이 되고, 앞 회차의 결정은 이어지지 않는다

고객 화면은 바꾸지 않는다(BIZ-094, 정한 것 3).

### 2.2 쓰는 자료

| 자료 | 스킬 어디에 |
|---|---|
| 공고 분석(요약, 필요 서류, 매트릭스, 평가 항목 구조, 사실 목록) | STEP 2 과업 개요, STEP 4 요구 내용, STEP 5 자격, 캡처플랜 1장 |
| 같은 공고번호의 다른 공고(사전 조사, 사전 공고, 특별 공고, 정정) | STEP 7 징후 1, 2, STEP 2 일정 |
| 같은 기관의 다른 공고 | STEP 3 발주처 동향(웹 자료 대신) |
| 낙찰 공고와 미 연방 계약(검색 도구) | STEP 3-A 발주 이력, STEP 6 경쟁사, 캡처플랜 3장, Bid/No-Bid 결정 수익성의 가격 기준 |
| 고객 회사(회원 칸)와 고객 서류 사실 | STEP 5 자격, 캡처플랜 4장, 스코어카드 자사 점수 |

웹 검색은 쓰지 않는다. 발주처 뉴스, 감사 지적, 상위 계획, 경쟁사 홈페이지가 필요한 칸은 미상으로 두고 출처에 "웹 자료 미사용" 을 기재해 확인 필요에 올린다.

### 2.3 입찰 분석 워크플로우 `bid-analysis` (Aimbase, 정의는 `docs/workflows/bid-analysis.steps.json`)

입력(서버가 생성): `bidRequestId`, `analysisId`

| 순서 | 단계 | 종류 | 하는 일 |
|---|---|---|---|
| 1 | report | AGENT_CALL(연결 cli-runner-bidding-tools-001, 스킬 sam-proposal 00, 01) | get_bid_analysis_input(step REPORT)으로 자료를 조회하고, search_award_history 로 발주 이력과 경쟁사 실적을 찾아 종합 분석 리포트를 쓴다. save_bid_analysis(part REPORT) |
| 2 | capture_plan | AGENT_CALL(같은 연결, 스킬 00, 11) | get_bid_analysis_input(step CAPTURE_PLAN)으로 종합 분석 리포트와 자료를 조회해 캡처플랜을 쓴다. 경쟁사 실적이 더 필요하면 search_award_history. save_bid_analysis(part CAPTURE_PLAN) |
| 3 | decision | AGENT_CALL(같은 연결, 스킬 00, 02) | get_bid_analysis_input(step DECISION)으로 종합 분석 리포트와 캡처플랜을 조회해 Bid/No-Bid 결정을 쓴다. save_bid_analysis(part DECISION) |

세 단계로 나눈 이유: 한 단계가 셋을 한 번에 쓰면 저장 도구에 전달할 본문이 한 턴의 출력 한도에 걸리고, 앞 산출물을 다시 읽어야 하는 뒤 단계의 도구 응답이 앱 도구 응답 한도(기본 2.5만 토큰, CR-169 2.11)를 초과한다. 단계마다 필요한 것만 조회한다(2.7).

지시문 요지(세 단계 공통):
- 스킬의 해당 장을 따른다. 01 의 STEP 0, 1 은 공고 분석이 했으니 다시 하지 않고 매트릭스의 REQ ID 를 그대로 쓴다
- 스킬이 말하는 산출물 파일(`0-capture/`, `2-decision/`)은 생성하지 않고 결과는 save_bid_analysis 로만 저장한다
- 발주 이력은 공고의 NAICS, PSC 로 먼저 찾고, 제목 핵심어와 공고번호로 넓힌다. 찾은 낙찰사를 업체 이름으로 다시 찾아 경쟁사 실적을 본다(스킬 01 STEP 3-A, 6)
- 조사한 값에는 모두 확신도(확정, 추정, 미상)와 출처(공고번호, 계약번호, 고객 서류 이름, "공고 분석", "참가 자격 답" 등)를 단다(BIZ-093)
- 고객 회사 사실은 회원 칸, 고객 서류 사실, 참가 자격 답에서만 쓴다. 없으면 추측하지 않고 미상으로 두어 확인 필요에 올린다(BIZ-093, BIZ-089 와 같은 원칙). 스킬이 "사용자에게 질문" 하라는 자리는 확인 필요 목록이다
- 점수에는 근거를 단다(스킬 02 "근거 없는 점수 금지"). Pwin 과 판정은 쓰지 않는다. 서버가 계산한다
- 보고 글은 한국어, 공고 요구 문장 인용은 영어 원문 그대로
- 저장이 거부되면 응답의 틀린 곳을 수정해 다시 저장한다

| profitability | priceBasis{rangeUsd, piids[]}(가격 기준: 비슷한 계약의 금액 범위와 계약번호), scenarios[{percent, priceUsd, margin}](기준 금액의 90, 85, 80% 가격 시나리오와 이익률), costNote. 원가는 고객 자료가 없으면 "고객 원가 자료 필요" 로 두고 이익률은 미상 |
| risks | [{area FINANCIAL, TECHNICAL, CONTRACT, risk, probability H, M, L, impact H, M, L}] |
| conditions | 조건부 Go 면 그 조건들 |
| advice | 결정 조언. No-Go 가 맞아 보이면 관계 구축이나 정보 획득 목적의 참여 여부도 기재한다 |

**확인 필요** (세 단계 모두 추가할 수 있다): questions[{target CUSTOMER, ADMIN, question, reason, field}]. 저장 때 앞 단계 것 뒤에 이어 붙인다. 같은 단계를 다시 저장하면(꼴이 틀려 거부된 뒤 등) 그 단계 것만 바꾼다

### 2.5 서버 계산 (BIZ-091)

Bid/No-Bid 결정(DECISION)을 저장할 때 서버가 계산해 회차에 둔다.

- 업체마다 가중 점수(%) = Σ(팩터 점수 x 정책 가중치) / 5, 가중치 합 100 기준, 소수 첫째 자리. Pwin 은 자사(OUR_COMPANY)의 값이다
- 판정: 정책 문턱(초기값 70, 50, 30)으로 70 이상 STRONG_GO, 50 이상 CONDITIONAL_GO, 30 이상 WEAK, 그 아래 NO_GO. 자격에 resolvable false 가 하나라도 있으면 점수와 상관없이 NO_GO 이고 판정 이유에 그 항목을 기재한다(스킬 02 축 2)
- 강점과 약점: BCC 테마마다 자사 점수에서 경쟁사 최고점을 뺀 값이 +1 이상이면 강점, -1 이하면 약점. 경쟁사가 없으면 비운다(스킬 02 객관적 강약점)
- 핵심이슈 순위: 관련자 이슈 점수 = 영향력 x 중요도, 묶은 이슈 점수 = 그 이슈에 속한 관련자 이슈 점수의 합, 높은 순(스킬 11 2.2)

신규 표 `bid_analyses`(V59). 입찰 건 하나에 회차 여러 줄, 지금 분석은 가장 늦게 시작한 회차다.

| workflow_run_id, started_at, finished_at, failure_reason | 워크플로우 회차와 시각, 실패 사유 |

- 워크플로우가 끝났는데 Bid/No-Bid 결정이 저장되지 않았으면 분석 실패이고 사유는 "Bid/No-Bid 결정이 저장되지 않음" 이다. 그때까지 저장된 종합 분석 리포트와 캡처플랜은 그대로 두고 보인다
- 본문의 꼴이 틀리면 저장을 거부하고 틀린 곳을 응답한다. 앞 단계가 없으면 거부한다(캡처플랜은 종합 분석 리포트 뒤, Bid/No-Bid 결정은 캡처플랜 뒤)

### 2.9 상태 전이

| 전이 | 바뀌는 것 |
|---|---|
| DOCS_RECEIVED 에서 ANALYZING | 진입 때 읽을 대상이 없고 읽는 중인 후보도 없으면 입찰 분석을 바로 시작한다. 아니면 읽기 회차가 끝날 때 시작한다(BIZ-090) |
| ANALYZING 에서 GENERATING | 지금 분석의 관리자 결정이 GO, CONDITIONAL_GO 가 아니면 409 `BID_DECISION_REQUIRED`(BIZ-092). 읽는 중 가드(BIZ-087)를 먼저 보고, 읽는 중이 아닐 때 결정을 본다 |
| ANALYZING 에서 CLOSED (신규) | 막지 않는다. 고객 알림은 지금처럼 없다 |

- 읽기 회차가 끝날 때(결과 마감 뒤) 서버는 그 회차가 읽은 내용을 후보 서류로 가진 입찰 건 가운데 분석 단계이고 입찰 분석 회차가 없는 건마다 읽는 중인 후보가 없으면 입찰 분석을 시작한다. 같은 내용을 다른 입찰 건의 회차가 읽은 경우도 이것으로 잡힌다. 그 회차가 읽은 내용을 쓰지 않는 건은 살피지 않는다
- 이미 회차가 있는 건은 자동으로 다시 분석하지 않는다. 다시 읽기 뒤 신규 사실을 반영하려면 관리자가 다시 분석을 누른다
- 배포 전부터 분석 단계에 있던 건은 회차가 없다. 그 건이 쓰는 서류 내용을 다른 건의 읽기 회차가 읽으면 그때 시작된다. 다시 분석하거나 분석 없이 결정을 기록하면 문서 작성 중으로 전환된다
- 분석 단계를 거쳐 종료한 건도 고객 서류 읽기 영역과 입찰 분석 영역을 보인다. 고객 서류 읽기 영역의 "분석 시작 전" 판단에 상태 이력을 더한다. 지금 상태가 분석 단계 이후이거나, 종료한 건은 상태 이력에 분석 단계 진입이 있으면 시작된 것이다(읽기 줄 유무로 판단하면 후보가 없는 분석 단계 건이 시작 전으로 보인다)

## 3. 정한 것

4. 스킬 전체 차용, Aimbase 소스는 수정하지 않고 워크플로우 정의와 스킬 묶음만 올린다(10/24 20:57, 20:59, CR-169 정한 것 3, 4)
