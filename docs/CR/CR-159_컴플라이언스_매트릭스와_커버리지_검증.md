## 1. 실측 (2026-10-12 소스)

### 1.1 공고 분석과 제안서

- 공고 분석은 Aimbase 워크플로우가 파일마다 근거(파일, 쪽, 원문 인용)를 단 fact 를 뽑고 검증한 뒤 `save_opportunity_analysis` 로 저장한다(`docs/workflows/opportunity-analysis.steps.v3.json:89`, 130)
- 평가 기준은 글 한 덩어리다(`AnalysisResultDto.java:52`). 평가 항목 구조를 담을 `factor_tree_json` 칸과 저장 함수가 있지만 부르는 곳이 없어 늘 비어 있다(`Notice.java:75`, 254). 제안서 설계 입력은 이 칸을 그대로 전달하고, 비면 워크플로우가 본문에서 발췌한다(`ProposalMcpTool.java:217`)
- 제안서 설계 단계는 절마다 `requirementRefs` 를 저장한다. 설명은 "Section L/M 발췌 ID 배열" 이지만 그 ID 를 매기는 곳이 없어 설계 단계가 그때그때 지어 쓴다(`ProposalMcpTool.java:73-98`)
- 절 작성 단계가 받는 것은 절 범위, 그 ID 목록, 참고 샘플이다. 요구 원문은 받지 않는다(`ProposalMcpTool.java:283-307`)
- 검증은 절마다 본문 0개와 최소 분량 미달(`VerificationLogService.java:151-162`), 그리고 원문에 없는 문장과 원문 항목 누락을 보는 LLM 검증이다. 요구 하나하나가 제안서에 답해졌는지 세는 곳은 없다

### 1.2 컴플라이언스 모듈

- 요구 항목 표(`OpportunityRequirementItem`): 공고 분석의 제출 서류로 채운다(CR-141, BIZ-045). 다시 분석하면 항목 열쇠(`sourceKey`)로 같은 줄을 찾아 고쳐 쓰고, 분석에서 사라진 줄은 이어 둔 충족 매핑과 함께 지운다(`RequirementSyncService.java:54-97`). 줄 상세는 JSON 칸에 들어간다(충족 주체, 필수 여부, 서식, 쪽수, 출처, 평가 항목)
- 막는 항목(`isBlocker`)은 필수이면서 충족 주체가 고객 업로드인 줄뿐이다(`RequirementSyncService.java:146-148`)
- 요구 항목을 읽는 곳: 고객 공고 요구사항 API(`OpportunityController.java:90-96`), 제출 전 검사(`PreCheckService.java:116`, 223, 252, 플랫폼 생성 줄도 고객 화면에 목록으로 보인다), 제안서 워크플로우 입력(`AIWorkflowService.java:383`), MCP `get_opportunity_requirements`(`OpportunityMcpTool.java:118`), 제출 준비 검사(`ComplianceService.java:84`)
- 충족 매핑 표(`RequirementFulfillmentMap`): 입찰 요청 하나와 요구 항목 하나에 한 줄(`V15` 유일 제약). 고객 서류 연결(`CLIENT_DOCUMENT`)은 제출 전 검사가 만든다(`PreCheckService.java:363`). 제안서 절 연결(`DOCUMENT_SECTION`)을 만드는 곳은 없다
- 매트릭스 생성 함수(`ComplianceService.generateComplianceMatrix`, 229행), 매핑 함수(`mapRequirement`, 153행), 제출 준비 검사(`validateBidRequest`, 47행)는 부르는 곳이 없다. API 도 화면도 없다
- 상태 전이 검사에서 `getBlockers` 를 부르는 줄은 주석으로 남아 있다(`BidFSMService.java:255-256`). 실제 막기는 고객 서류 빈칸 확인이다(`BidFSMService.java:156`)
- T1-1 은 BID-COMP-001, 002 를 "구현완료(기존)" 로 적고 있다. 고객 서류 연결만 동작하고 제안서 절 연결과 충족 검증은 없다

## 2. 설계

### 2.1 컴플라이언스 매트릭스 뽑기 (Aimbase 공고 분석 워크플로우)

스킬 묶음 `sam-proposal` 의 1단계 참고서를 읽고 뽑는다. 뽑는 규칙은 스킬 원문(`01-rfp-analysis.md` STEP 1, STEP 4)을 미국 연방 입찰에 맞춘 것이다.

1. 출처: Section L(작성 지시), Section M(평가 기준), Section C 또는 PWS·SOW(과업), 수정 공고(Amendment), 질의응답. 흩어진 요구를 전부 뽑는다
2. 한 문장에 요구가 둘이면 두 줄로 나눈다
3. 원문을 고쳐 쓰지 않는다. 영어 원문 그대로 두고 번역을 따로 단다
4. 줄마다 출처(파일, 쪽, 조항)와 원문 인용을 단다. 지금 fact 와 같은 근거 검증(인용을 원문에서 찾지 못하면 버림)을 거친다
5. 구분: Shall(shall, must, will), Should(should), May(may, 가점)
6. 요구 동사(describe, provide, demonstrate, submit 등)를 남긴다. 동사가 답의 형태를 정한다
7. 충족 주체: 지금 분류(고객 업로드, 플랫폼 생성, 정부 양식)를 그대로 쓴다
8. 분류: 기술, 서식, 제출, 마감, 자격, 그 밖 가운데 하나
9. 평가항목: 그 요구가 걸린 Section M 평가 항목
10. 질의 후보: 모호하거나 해석이 갈리는 줄은 질의 후보로 표시하고 모호한 점과 질의(안)을 단다
11. 평가 항목 구조도 같이 낸다. 항목, 하위 항목, 상대 중요도, 평가 방식(LPTA, Best Value Tradeoff)

### 2.2 저장 (입찰대행 서버, 새 표 없음)

- 분석 워크플로우는 `save_opportunity_analysis` 에 매트릭스(`complianceMatrix`)와 평가 항목 구조(`factorTree`)를 같이 보낸다. 공고문에 매트릭스 칸(`compliance_matrix_json`)을 추가해 받은 그대로 담고, 평가 항목 구조는 지금 있는 `factor_tree_json` 에 담는다. 관리자 수정과 다시 채우기도 이 칸에서 요구 항목을 다시 맞춘다(제출 서류와 같은 길)
- 매트릭스 줄은 지금의 요구 항목 표에 넣는다. REQ ID 가 있는 줄이 매트릭스 줄, 없는 줄이 지금의 제출 서류 줄이다
- 지금 요구 항목을 읽는 곳(1.2 의 다섯 곳)은 제출 서류 줄만 읽게 한다. 고객 화면, 제출 전 검사, 지금 워크플로우 입력은 바뀌지 않는다
- 항목 열쇠는 출처 조항과 원문으로 만든다. 다시 분석해도 같은 원문이면 같은 줄이 이어지고, 이어 둔 충족 매핑도 그대로 남는다
- REQ ID(REQ-001 부터)는 공고 안에서 처음 들어온 순서로 매긴다. 같은 줄은 다시 분석해도 번호를 바꾸지 않고, 새 줄은 뒤 번호를 받는다. 공고마다 마지막으로 준 번호를 두어 지운 번호를 다시 쓰지 않는다
- 다시 분석에서 사라진 줄은 제출 서류 줄과 같이 이어 둔 충족 매핑과 함께 지운다(BIZ-045). 그 번호를 대응 REQ ID 로 들고 있는 제안서 절은 커버리지 검증이 "매트릭스에 없는 ID" 로 잡는다
- 줄 상세(원문, 번역, 출처 파일, 쪽, 조항, 인용, 요구 동사, 충족 주체, 평가항목, 질의 후보, 모호한 점, 질의(안))는 지금처럼 JSON 칸에 담는다. REQ ID 와 구분은 열로 꺼낸다(조회, 정렬, 커버리지 계산용). 분류는 지금 분류 칸의 값(TECHNICAL, FORMAT, SUBMISSION, DEADLINE, ELIGIBILITY, OTHER)으로 넣고 제출 서류 줄의 DOCUMENT 는 쓰지 않는다
- 매트릭스 줄은 막는 항목이 아니다. 고객 서류 막기는 지금처럼 제출 서류 줄만 한다(BIZ-046)
- 고객이 서류를 올리는 길은 매트릭스 줄을 받지 않는다. 매트릭스 줄 id 로 올리면 찾을 수 없음으로 답한다(구현 중 더함)
- 매트릭스를 내지 않은 공고(옛 분석)는 매트릭스 줄이 없다. 이때 아래 2.3, 2.4 의 검사는 하지 않는다

### 2.3 제안서가 매트릭스를 쓰게 한다 (Aimbase 제안서 워크플로우 + 서버 도구)

1. 설계 입력(`get_proposal_design_input`): 매트릭스 줄(REQ ID, 원문, 구분, 요구 동사, 충족 주체, 평가항목)을 같이 준다. 평가 항목 구조도 이제 채워져 간다
2. 설계 저장(`save_proposal_structure`): 절마다 대응 REQ ID 는 매트릭스의 REQ ID 만 받는다. 매트릭스에 없는 ID 가 있으면 저장을 거부하고 그 ID 들을 돌려준다. 저장되면 응답에 어느 절에도 안 걸린 대상 줄(2.4)의 REQ ID 목록을 같이 준다
3. 절 정보(`get_section_context`): 그 절의 대응 REQ ID 마다 원문, 번역, 요구 동사, 구분, 평가항목을 같이 준다
4. 검증 입력(`get_section_verify_input`): 절 정보와 같은 요구 원문을 같이 준다
5. 검증 저장(`save_verification_result`): 제안서 절 검증이 대응 REQ ID 마다 본문이 답했는지(답함, 본문 인용, 사유)를 같이 낸다. 답했으면 그 입찰 요청의 충족 매핑을 제안서 절(`DOCUMENT_SECTION`, 충족)로 채운다. 답하지 않았으면 누락으로 둔다. 다만 다른 절이 이미 답한 것으로 채워 둔 매핑은 건드리지 않는다
6. 설계를 다시 저장하면 절을 지우고 다시 만들어 절 id 가 바뀐다. 그 문서의 제안서 절 충족 매핑을 같이 지우고, 다시 만든 절의 검증이 다시 채운다(구현 중 더함)

### 2.4 커버리지 검증 (입찰대행 서버, AI 없음)

- 대상: 구분이 Shall 이면서 충족 주체가 플랫폼 생성인 매트릭스 줄
- 제안서 문서 하나에 대해 센다. 볼 때마다 계산하고 따로 저장하지 않는다
  - 매핑 안 된 REQ: 대상 가운데 어느 절의 대응 REQ ID 에도 없는 줄
  - 누락 REQ: 대상 가운데 이 문서의 절로 충족된 매핑이 없는 줄(매핑 안 된 REQ 포함)
  - 매트릭스에 없는 ID: 절이 들고 있는데 매트릭스에 없는 REQ ID
  - 커버리지: 대상 수 가운데 누락 REQ 가 아닌 수(스킬 `check_coverage.py` 의 커버율과 같은 뜻)
- 누락 REQ 나 매트릭스에 없는 ID 가 하나라도 있으면 관리자 화면에 경고를 표시한다. 제출을 막지는 않는다(관리자가 판단)
- 쓰이지 않던 매트릭스 생성 함수(`generateComplianceMatrix`)를 이 계산으로 고쳐 쓴다

### 2.5 관리자 화면

- 공고문 관리 상세: "컴플라이언스 매트릭스" 영역. 줄마다 REQ ID, 요구사항(원문 그대로), 번역, 출처, 구분, 요구 동사, 평가항목, 충족 주체. 아래에 질의 후보(REQ ID, 모호한 점, 질의(안)). 읽기만 한다
- 제안서 트리: 위에 커버리지(대상 수, 충족 수, 비율), 누락 REQ, 매트릭스에 없는 ID. 절마다 대응 REQ ID 와 그 번호의 충족 여부
- 고객 화면은 바꾸지 않는다

## 3. 정한 것

1. 워크플로우 적용 시점: Aimbase 범용 스킬 묶음이 나온 뒤에 워크플로우를 바꾸고, 그 전에는 서버와 화면만 만든다(사용자 10/12 22:29 "1")
2. 고객 화면은 이번 범위가 아니다
3. 매트릭스 줄은 새 표가 아니라 요구 항목 표에 넣는다. 쓰이지 않던 매트릭스 생성 함수와 제안서 절 충족 매핑을 살려 같은 구조 둘을 두지 않는다
4. 사라진 줄은 지금 규칙(BIZ-045)대로 지운다. 번호를 다시 쓰지 않으므로 옛 번호를 든 절은 커버리지 검증이 잡는다
5. 커버리지는 저장하지 않고 볼 때 계산한다

## 6. 시험

- 매트릭스: 실제 공고 3건(서비스, 공사, 물품)에서 줄 수, 원문 그대로 여부, 근거 인용 검증 통과율
- 다시 분석: 같은 공고를 두 번 분석해 같은 줄의 REQ ID 와 충족 매핑이 그대로인지, 사라진 줄의 번호를 새 줄이 받지 않는지
- 커버리지: 요구 하나를 일부러 뺀 제안서에서 누락 REQ 로 잡히는지, 매트릭스에 없는 ID 를 설계 저장이 거부하는지
- 고객 화면: 매트릭스 줄이 생긴 공고의 제출 전 검사와 공고 요구사항 API 결과가 전과 같은지
- 막는 항목: 매트릭스 줄이 서류 접수 전환을 막지 않는지
