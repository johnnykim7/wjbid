## 1. 왜

낙찰된 실제 입찰 건(W90VN825R0006 캠프 케이시+용산 그라운드 관리, 31억 낙찰)으로 서류 등록, 작성 요청, AI 제안서 작성을 상용에서 처음부터 끝까지 시험하려 한다. 공고는 관리자 「테스트 공고 추가」(CR-120)로 만든다. 그런데 지금은 그 공고를 공개하면 실제 고객에게 보이고 알림 메일도 나간다.

## 2. 실측 (2026-11-05, 11-06 develop 소스, 상용 자료)

- 「테스트 공고 추가」로 만든 공고는 원본 JSON 에 `{"source":"MANUAL_TEST"}` 표시만 있고 나머지는 수집 공고와 똑같이 다뤄진다(`OpportunityService.createManual`). 상용에 4건 있다(TEST-CR120-A, TEST-SMOKE-AI-0001, PROD-CR120-CHECK, TEST-1782017871068)
- 고객의 공고 검색, 첫 화면 목록과 건수, 메뉴 속 화면(사전 공고, 변경 공고, 월별 동향, 업종별 발주, 낙찰 업체, 미 연방 계약 자료의 본 공고 잇기)은 모은 공고 전부(지운 것 제외)를 읽는다(`OpportunityRepository.MARKET_SOURCE_SELECT`). 11/5 상용 고객 공고 검색에서 TEST-SMOKE-AI-0001 "Grounds Maintenance Services for Test Co" 가 나온다
- 공고문을 공개하면 공개 공고문 목록, 최근 공고문, 적격성 진단 목록에 들어간다(`NoticeRepository.findVisible`, `findVisibleRecentlyPosted`)
- 공고문을 처음 공개하면 오늘 회원 기간 안의 고객 전원에게 "신규 입찰 공고 등록" 메일이 나간다(`NoticeService.publish`, `NotificationEventListener.onOpportunityApproved`)
- 제안서 작성 입력, 문서 구성, 입찰 분석, 적격성 진단은 공개 공고문만 읽는다(`AIWorkflowService.build3PipelineContext` 외). 공고문을 숨겨 두면 시험이 되지 않는다
- 입찰 신청은 공고문 번호로 공고문을 찾는다(`BidRequestController`, `noticeService.findById`). 공고문 상세는 번호로 연다(`findByIdAndVisibility`). 그래서 목록에서 빠져도 주소로는 열고 신청할 수 있다

## 3. 바꾸는 것

| 순번 | 자리 | 지금 | 바꾼 뒤 |
|------|------|------|--------|
| 1 | 공고 표 | 테스트 공고를 가르는 칸이 없다 | `opportunities.test_notice` (BOOLEAN, 기본 FALSE). 「테스트 공고 추가」가 TRUE 로 만든다. 마이그레이션 V61 이 원본 JSON 에 MANUAL_TEST 표시가 있는 기존 줄을 TRUE 로 채운다 |
| 2 | 모은 공고 조회 | 지운 것만 뺀다 | 테스트 공고도 뺀다. 공고 검색, 첫 화면, 메뉴 속 화면, 낙찰 업체, 미 연방 계약 자료의 본 공고 잇기, 입찰 분석의 같은 기관 최근 공고가 모두 이 조회를 쓴다 |
| 3 | 공개 공고문 목록, 최근 공고문 | 공개된 공고문 전부 | 테스트 공고의 공고문은 뺀다. 적격성 진단 목록도 공개 공고문 목록을 쓰므로 같이 빠진다 |
| 4 | 신규 공고 알림 | 처음 공개하면 회원 고객 전원에게 보낸다 | 테스트 공고면 보내지 않고 기록만 남긴다 |

그대로 두는 것: 공고문 번호로 연 상세와 요구 서류, 첨부, 입찰 신청, 제안서 작성 입력, 문서 구성, 입찰 분석의 그 공고 입력, 관리자 화면 전부(원본 공고 목록, 공고문 관리, 입찰 관리). SAM 수집은 이 칸을 건드리지 않는다.

규칙은 BIZ-099 로 둔다. 화면과 API 응답 모양은 바뀌지 않는다.
