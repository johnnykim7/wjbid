## BL-001 · 고객 포털 비밀번호 재설정 기능

| | |
|---|---|
| 등록일 | 2026-10-10 |
| 출처 | CR-131 로그인·회원가입 화면 개편 중. 로그인 화면의 "비밀번호 찾기" 링크가 아무 데로도 가지 않았다(frontend/customer-portal/src/pages/LoginPage.tsx:101, href="#"). 사용자 10/10 22:41 /전승으로 CR-131 에서는 고객센터 이메일 안내 문구로 바꾸고, 재설정 기능 신설은 백로그로 둔다 |
| 담당(예정) | bidding-agency-platform |
| 상태 | 대기 |

**무엇**

고객이 비밀번호를 잊었을 때 스스로 다시 설정할 길이 없다. CR-131 뒤에는 로그인 화면이 고객센터 이메일로 가입 이메일을 보내 달라고 안내하고, 운영자가 손으로 처리한다. 메일로 재설정 링크를 보내 고객이 직접 새 비밀번호를 정하는 기능이 필요하다. 백엔드(재설정 토큰, 만료, 한 번만 쓰기, 메일 양식)와 고객 화면(재설정 요청, 새 비밀번호 입력)이 함께 걸린다.

**왜 남겼나**

새 API 와 메일 양식, 화면이 들어가는 중규모 이상이라 T1 부터 캐스케이드가 필요해 화면 개편(CR-131)과 떼었다. 1:1 문의 화면도 아직 서버에 닿지 않아(pages/SupportPage.tsx, 제출이 알림창만 띄움) 안내처로 쓸 수 없다. 가입 회원이 늘어 이메일 문의로 감당하기 어려워지기 전에 한다.

## BL-003 · 관리자 입찰 상세에 공고 제목, 회사명, 고객 제출 문서가 비어 보인다

| | |
|---|---|
| 등록일 | 2026-10-26 |
| 출처 | CR-170 합동시험(상용 10/26 04:26). 관리자 [입찰 요청 관리] 에서 아무 입찰 건 상세를 열면 보인다 |
| 담당(예정) | bidding-agency-platform |
| 상태 | 완료(CR-182, 10/26 22:48 상용 배포) |

**무엇**

① 공고 정보의 제목, 기관, 공고번호와 고객 정보의 회사명, 이메일, 기타 정보의 서비스 레벨이 모두 "-" 로 나온다. 화면은 응답 안에 opportunity, member 묶음이 있다고 보고 읽는데(`BidRequestDetailPage.tsx:48-71`), 서버 `GET /admin/bid-requests/{id}` 는 opportunityTitle, agencyName, solicitationNumber, memberEmail 처럼 펼친 칸으로 준다(상용 응답 실측, 서비스 레벨 칸은 응답에 없음).

② 고객이 올린 서류가 있어도 고객 제출 문서에 "고객이 업로드한 문서가 없습니다" 가 나온다. 화면은 `/api/client-documents/{입찰 건 id}` 를 부르는데(`api/client.ts:173`) 그 주소가 없어 404 이고, 서버 주소는 `/bid-requests/{bidRequestId}/client-documents` 다(`ClientDocumentController.java:22`). 같은 화면의 고객 서류 읽기 영역에는 그 서류가 보인다.

**왜 남겼나**

이번 변경 전부터 있던 결함이고 CR-170(입찰 분석) 범위 밖이라 새 CR, 새 창에서 한다. 관리자가 상세에서 어느 공고, 어느 고객 건인지 알아볼 수 없으므로 다음 관리자 화면 작업 전에 고친다.

## BL-004 · 제안서 작성이 그 공고 유형의 성공 제안서 가이드를 쓰지 않는다

| | |
|---|---|
| 등록일 | 2026-10-26 |
| 출처 | CR-170 합동시험(상용 10/26 04:52 b001 문서 작성, IT-13-028). 분류된 공고(GROUND_MAINTENANCE)의 입찰 건을 GENERATING 으로 넘기고 Aimbase 실행 기록의 입력을 보면 보인다 |
| 담당(예정) | bidding-agency-platform |
| 상태 | 대기 |

**무엇**

① 성공 제안서 가이드(successGuide)가 제안서 작성 어느 단계에도 가지 않는다. 지금 작성 순서(설계, 절 작성, 묶기, CR-028)의 설계 실행 입력은 bidRequestId, documentId, documentType, opportunityText 뿐이고 절 작성 입력은 sectionId 뿐이다(`AIWorkflowService.java:201-205`). 설계 입력 도구(get_proposal_design_input)와 절 맥락 도구(get_section_context)도 가이드를 주지 않는다(`ProposalMcpTool.java:330-345`). 가이드와 참조 사용 규칙(referenceUsagePolicy)을 싣는 곳은 옛 작성 길(`build3PipelineContext`, `AIWorkflowService.java:426-465`)뿐이고, 그 길은 관리자 검토 중 문서 한 건 다시 만들기만 쓴다.

② 참조 표본(referenceSamples)은 절 맥락 도구 결과로만 가고 실행 입력에는 없다. 그래서 IT-13-028 의 "입력의 referenceSamples" 는 실행 기록으로 확인할 수 없다. 사실 복붙 금지는 도구 설명 문장에만 있고 referenceUsagePolicy 칸으로는 없다.

**왜 남겼나**

CR-028(6/1) 때 생긴 결함이고 CR-170(입찰 분석) 범위 밖이라 새 CR, 새 창에서 한다. 그 CR 은 IT-13-028 과 IT-10-001 5번(성공 제안서 가이드를 따른다) 문구도 지금 작성 순서에 맞는지 같이 본다. 성공 제안서 자산(CR-013, CR-014)이 작성에 쓰이지 않는 채로 있으므로 다음 제안서 품질 작업 전에 고친다.

## BL-005 · 관리자 문서 편집 화면이 표가 든 AI 제안서를 빈 화면으로 연다

| | |
|---|---|
| 등록일 | 2026-10-26 |
| 출처 | CR-170 합동시험(상용 10/26 b001 문서 작성, IT-10-001 [편집]). 입찰 요청 상세에서 AI 가 묶은 기술 제안서(e6d443ad 2판, 본문 42,687자)를 [편집] 으로 열면 본문 칸이 비어 있다 |
| 담당(예정) | bidding-agency-platform |
| 상태 | 대기 |

**무엇**

AI 가 절마다 쓰고 서버가 묶은 제안서는 본문에 표(tableHeader, tableRow, tableCell)를 담는데, 관리자 문서 편집 화면의 편집기는 기본 글자 기능, 밑줄, 정렬, 안내 문구만 켜고 표 기능을 켜지 않는다(`DocumentEditPage.tsx:71-75`). 표 기능 꾸러미는 이미 받아 두었지만(`package.json:16-19`) 쓰지 않는다. 그래서 저장된 본문을 편집기에 넣는 순간(`DocumentEditPage.tsx:98`) 모르는 표 마디 때문에 본문 전체가 들어가지 않고 빈 화면이 된다. DB 의 그 판 본문에는 절 제목, 문단, 표가 다 들어 있다. 입찰 요청 상세의 생성 문서 목록에는 판 번호만 나오고 본문을 보는 다른 자리가 없다.

**왜 남겼나**

CR-169(문서를 절마다 쓰고 묶기) 때부터 있던 결함이고 CR-170(입찰 분석) 범위 밖이라 새 CR, 새 창에서 한다. 관리자가 AI 가 쓴 제안서를 화면에서 읽거나 고칠 길이 막혀 있으므로 다음 제안서 검토 작업 전에 고친다. 고친 뒤 IT-10-001 4번을 다시 판정한다.

## BL-006 · 제안서 작성이 고객 서류에 없는 회사 사실을 쓰고, 검증은 공고 제목만 보고 판정한다

| | |
|---|---|
| 등록일 | 2026-10-26 |
| 출처 | CR-170 합동시험(상용 10/26 b001 문서 작성, IT-10-001 5번, IT-12-034). 문서 작성 뒤 절 목록(proposal_section)과 검증 기록(verification_log)을 보면 보인다. 10/25 회차도 같은 비율이었다 |
| 담당(예정) | bidding-agency-platform |
| 상태 | 대기 |

**무엇**

① 작성 단계가 고객 서류에 없는 회사 사실을 단정해 쓴다. b001 기술 제안서 과거 실적 절은 고객 서류에 계약 1건(Camp Humphreys Plumbing Repair)만 있는데 "이 용역과 같은 종류의 작업을 수행한 두 번째 계약을 더해 REQ-058과 REQ-059가 요구하는 2건 이상을 충족하며, 두 계약 모두 발주처 기록으로 만족(Satisfactory) 이상의 평가를 증명" 이라고 쓴다. 같은 문서 안에 "[Client data required: 계약 2가 ...]" 자리 표시가 함께 있어 문장끼리도 어긋난다.

② 검증 단계가 받는 공고 원문(opportunityText)이 공고 제목, 기관, 공고번호, 본문 한 줄뿐이다(`ProposalMcpTool.java:513-526`, 상세 본문이 없는 공고는 제목 한 줄). 작성 단계는 절 맥락 도구로 작업 범위와 요구사항을 받는데, 검증 단계는 공고가 요구한 제출 형식, 순서 같은 내용을 볼 수 없어 "공고 본문에 그런 내용이 없다" 로 떨어뜨린다. b001 의 검증 기록에 이 사유의 미통과가 여러 번 있다.

결과로 b001 의 절 8개 가운데 7개가 두 번 시도 뒤 다시 써야 함(NEEDS_REGEN)으로 끝났다(표지 1, 기술 제안서 7 가운데 장비 계획 1개만 통과). ①은 맞게 떨어진 것이고 ②는 잘못 떨어진 것일 수 있어, 두 원인을 나눠 본다.

**왜 남겼나**

CR-031(검증), CR-169(절마다 작성) 때부터 있던 것이고 CR-170(입찰 분석) 범위 밖이라 새 CR, 새 창에서 한다. 고객에게 없는 실적을 있다고 쓴 제안서가 그대로 나가면 입찰 자격 문제가 되므로 다음 제안서 품질 작업에서 BL-004 와 같이 본다.
