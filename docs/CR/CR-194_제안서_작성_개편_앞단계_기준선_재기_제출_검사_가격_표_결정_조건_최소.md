## 2. 실측 (2026-11-08 develop 소스, 상용 자료)

- 시험 건(신청 3e2cd50a, qa-cr143)은 검토 대기이고 문서는 기술 제안서 1건, 회사 칸은 UEI, CAGE, 주소가 비어 있다

- 실제 낙찰본의 가격 엑셀은 줄마다 수량 x 단가이고 금액을 반올림하지 않는다. 단가에 소수가 있다(0010 은 73258.038...). 기본 연차 14줄이다

## 3. 기준선 재기 (들이는 순서 1)

소스를 고치지 않고 상용에서 잰다. 한 번에 입력 하나만 바꾼다.

| 순번 | 조건 | 바꾼 입력 | 쓰는 건 |
|---|---|---|---|
| 1 | 같은 다섯 파일과 지금 시험 계정 | CR-189 효과 | 시험 건 3e2cd50a 를 시험 공고 다시 분석 뒤 다시 쓰기 |
| 2 | 1 에 회사 정보만 채움 | 회사 이름, 주소, UEI, CAGE, 담당자 | 같은 건을 다시 쓰기 |
| 3 | 2 에 서류만 원재료로 바꿈 | 고객 서류 | qa-reg-1011 로 같은 공고에 신청, 회사 정보는 2 와 같게 |

- 조건 3 만 따로 신청하는 이유: 검토 대기에서는 서류를 바꿔 읽는 길이 없고, 같은 회원은 다시 신청할 수 없다
- 원재료는 제출본에서 회사가 작성한 서술 쪽을 뺀 증빙과 명단 쪽만 떼어 만든다. 칸은 원래 다섯 칸 그대로다

| 순번 | 칸 | 쓰는 쪽 |
|---|---|---|
| 1 | 사업자 등록 | A-1 2 ~ 12쪽 (등록증, 수첩, 인증서, 특허, SAM 상태, 담당자) |
| 2 | 수행경험 | A-2 8 ~ 23쪽 (실적 목록, 사진) |
| 3 | 장비계획 | A-4 5 ~ 16쪽, 23 ~ 28쪽 (보유 장비 목록과 사진, 임대차 계약서) |
| 4 | 핵심인력 | A-5 전체 (이력서, 자격, 경력, 4대 보험) |
| 5 | 과거 실적 자료 | B 전체 (실적 표, 사진) |

- 다시 쓰기는 절과 본문을 지우고 다시 만든다(`ProposalService.saveStructure`). 조건마다 끝나면 결과를 읽어 `docs/기록/기준선_CR-194/` 에 옮겨 둔 뒤 다음 조건을 돌린다. 조건 1 전에 지금 매트릭스와 절도 옮겨 둔다(다시 분석으로 REQ 번호가 바뀌면 F-10 표와 맞대기 위해)
- 작업 흐름은 한 번에 하나만 돈다
- 재는 것: 절별 판정과 환각 수, 요구에 답하지 않은 줄, F-10 의 답이 있는 43줄 가운데 답한 줄, 가격 항목 줄 수(기대 66), 정부 양식 문서와 다섯 묶음, 장별 단어 수(비교 신호로만), 걸린 시간
- 기준선 결과를 사용자에게 보이고 사람이 정할 것 1(최소 단어를 끄는 자리)을 묻는다. 확인하지 못한 사실 1 에 따라 합의된 순서 4 가 다시 열릴 수 있다

## 4. 제출 검사 (들이는 순서 2)

산출물을 바꾸지 않는다. 읽어서 판정만 낸다. 관리자가 적는 것은 줄의 처리뿐이다.

### 검증 못 함

- 판정에 검증 못 함(`UNVERIFIED`)을 더한다. 작업 흐름이 실패하거나 이번 시도의 결과가 없으면 서버가 이 판정을 남긴다
- 검증 못 함은 통과가 아니다. 실패도 아니어서 자동 다시 쓰기는 돌지 않는다
- 검증 기록은 이번 시도 번호의 것만 읽는다

### 줄마다 상태

대상은 수준이 SHALL 인 매트릭스 줄 전부다. 채우는 쪽을 가리지 않는다.

| 순번 | 상태 | 뜻 | 정하는 쪽 |
|---|---|---|---|
| 1 | 충족 | 절 검증이 답했다고 남겼고 그 절의 사실 검증이 통과 | 서버 |
| 2 | 미충족 | 절 검증이 답하지 않았다고 남김 | 서버 |
| 3 | 검증 못 함 | 줄이 걸린 절이 검증 못 함이거나, 검증 뒤 입력이 바뀜 | 서버 |
| 4 | 확인 안 됨 | 어떤 기록도 처리도 없음 | 서버 |
| 5 | 답하지 않는 줄 | 제안서에서 답할 거리가 아니다. 사유와 공고 원문 근거 필수 | 관리자 |
| 6 | 동등 여부 확인 | 원문과 다른 증빙이다. 근거를 적어야 동등으로 풀린다 | 관리자 |
| 7 | 동등 인정 | 동등 여부 확인에 근거를 적어 푼 것 | 관리자 |
| 8 | 적용 미확인 | 적용이나 해석이 확인되지 않았다 | 관리자 |

- 처리는 줄마다 한다. 한꺼번에 처리하는 기능을 두지 않는다
- 낙찰했다는 사실이나 근거 없는 관리자 확인은 충족이 아니다. 관리자의 처리는 회사 사실을 만들지 않는다

### 제출 가능 판정

- 제출 가능은 사실 검증 통과와 다른 판정이다
- 다음이 모두 맞아야 제출 가능이다: SHALL 줄이 모두 충족, 답하지 않는 줄, 동등 인정 가운데 하나, 모든 절의 사실 검증이 통과, 결정 조건이 모두 해소, 가격 표 완료, 입력이 바뀌지 않음
- 맞지 않으면 이유를 항목으로 보인다
- 이번에는 보여 주기만 하고 입찰 상태 전이를 막지 않는다. 막을지는 진단 시험 뒤 사용자가 정한다

### 입력 묶음

- 합의 사항("승인과 검증 결과는 실행이 쓴 입력 묶음에 묶는다")을 검증 기록에 적용한다
- 절 검증을 저장할 때 공고 분석 시각, 절 근거 서류의 내용 해시, 회사 칸, 입찰 분석 회차를 검증 기록에 남긴다
- 지금 값과 다르면 그 절에 걸린 줄은 검증 못 함이다. 다시 검증하면 풀린다. 영향을 대조해 옛 결과를 다시 쓰는 길(갈린 것 B-4)은 두지 않는다

## 5. 진단 시험 (들이는 순서 3)

- 실제 낙찰본 본문(`docs/기록/토론_제안서작성개편/자료/원자료/실제제출본_본문`)을 전용 시험 건의 절 본문으로 넣고 절 검증을 돌린 뒤 제출 검사 결과를 낸다
- 결과를 F-10 줄별 표와 줄마다 맞대어 `docs/기록/기준선_CR-194/` 에 남긴다
- 낙찰본이 통과하도록 검사를 맞추지 않고, 낙찰했다는 사실을 판정 근거로 쓰지 않는다. 낙찰본의 답을 정답표나 자동 면제 목록으로 쓰지 않는다

## 6. 가격 표, 결정 조건, 최소 단어 (들이는 순서 4)

회차를 갈라 각각 기준선 조건 3 과 같은 입력으로 잰다. 조건 3 결과를 쓸 수 없으면 조건 2 로 잰다. 요구 누락이 늘지 않는지 본다. 차례는 가격 표, 결정 조건, 최소 단어다(최소 단어는 사용자 결정이 있어야 한다).

### 가격 표

- 표의 줄은 공고 분석의 가격 항목이다. 고객이 줄마다 단가를 넣는다. AI 는 단가를 정하지 않는다
- 서버가 금액(수량 x 단가, 반올림하지 않음), 연차별 소계, 합계를 계산한다. 화면에 넣은 금액을 받지 않는다
- 엑셀로 내보낸다
- 고객이 넣고 관리자는 보고 내보낸다. 건이 확정(CONFIRMED)되면 단가를 바꿀 수 없다
- 완료는 표가 있는지가 아니라 모든 줄에 수량과 단가가 있어 금액과 합계가 나왔는지로 본다. 가격 항목 칸이 비어 있으면(분석 전) 확인 안 됨, 빈 목록이면(공고에 가격 표 없음) 해당 없음이다
- AI 가격 절은 가격 일람 표를 자리표시로 그리지 않고 별도 가격 표 파일을 참조한다

### 결정 조건 전달

- 지금 입찰 분석의 결정 조건을 절 작성과 절 검증 입력에 `decisionConditions` 로 싣는다. 확인된 사실이 아니라 고칠 것 목록이다
- 본문은 정정을 마친 사실로 쓰지 않는다. 고치지 못한 자리는 자리표시로 둔다
- 조건마다 제출 검사에 미해결로 남고, 관리자가 해소 근거를 적어야 풀린다

### 최소 단어 끄기

- 하한을 없애는 것이지 짧게 쓰라는 것이 아니다. 필요한 표, 설명, 약속 문단은 남긴다
- 끄는 자리는 기준선 결과를 본 뒤 사용자가 정한다(결정메모 B-1 의 세 안). 정해지면 이 절에 적는다
- 끈 절은 설계가 값을 넣지 않고, 작성 지시문의 하한과 자체 보강을 적용하지 않으며, 서버 규칙 검사가 돌지 않는다
