# CR-126 SAM 수집 실패 알림 (키 만료 무경보 해소)

- **CR-ID**: CR-126
- **작성일**: 2026-08-13
- **규모**: 중규모 (신규 이벤트 + 알림 타입 + 스케줄러/리스너 변경)
- **상태**: 설계 완료, 구현 대기
- **원본 사건**: 2026-08-03 ~ 08-12 SAM.gov API 키 만료로 수집 9일간 전면 중단, 무경보

---

## 1. 배경 — 무엇이 일어났나 (실측)

`sam_api_call_log` 실측:

| 구간 | 상태 |
|---|---|
| ~2026-08-02 | 정상 (search 4/4 성공, HTTP 200) |
| 2026-08-03 | 마지막 성공 1건 + 에러 3건 → 이날 키 무효화 |
| 2026-08-04 ~ 08-12 | **전부 401** (하루 4콜 × 9일 = 36콜 전패) |

에러 본문: `{"code":"900901","message":"Invalid Credentials"}` — 인증 실패(쿼터 초과 아님).

**9일간 아무도 몰랐다.** 키 교체 후 첫 수집(2026-08-12 23:00)에서 공백기 공고 29건이
소급 적재되어 데이터 손실은 없었으나(스케줄러가 매회 최근 30일을 훑는 구조),
이는 **운 좋게 복구된 것이지 설계된 안전장치가 아니다.**

## 2. 원인 — 왜 조용했나 (3중)

| # | 원인 | 위치 |
|---|---|---|
| 1 | **실패 전용 알림 경로 부재** — 이벤트가 "수집 완료" 하나뿐 | `OpportunityCollectionScheduler:77` |
| 2 | **0건 스킵이 실패를 삼킴** — `targetNewCount == 0`이면 메일 스킵. "401로 0건"과 "원래 신규 없음"이 구분 불가 | `NotificationEventListener:62` (CR-015) |
| 3 | **에러가 로그에만 남음** — `log.error` 후 종료. 아무도 로그를 보지 않음 | `OpportunityCollectionScheduler:80-82` |

추가 실측: 401은 `OpportunityCollectorService:145-148`의 광범위 catch에서 `errors++`로만
집계되어 **HTTP status가 유실**된다. 따라서 errors 카운트만으로는 "키 만료"를 특정할 수 없다.

## 3. 설계 원칙

1. **실패는 성공 경로와 분리한다** — 0건 스킵 로직(CR-015)은 노이즈 차단 목적이므로 유지하되,
   실패 알림은 그 분기를 타지 않는 **독립 이벤트**로 발행한다.
2. **키 만료는 문구로 특정한다** — "수집 실패"가 아니라 "API 키가 만료된 것으로 보입니다"까지
   알려야 사람이 즉시 조치한다(이번 사건의 조치는 키 재발급 5분이었다).
3. **status 유실 문제는 기존 자산으로 우회한다** — CR-036이 이미 `sam_api_call_log.last_status`에
   401을 적재하고 있다. collector의 예외 처리 구조를 건드리지 않고 **이 로그를 조회**해 판별한다.
4. **알림 폭탄을 막는다** — 실패가 9일 지속되면 36통이 아니라 **하루 1통**. 기존 BIZ-012 멱등키 재사용.

## 4. 변경 명세

### 4-1. 이벤트 신설 — `CollectionFailedEvent`

| 필드 | 타입 | 설명 |
|---|---|---|
| keyword | String | 수집 키워드 (411TH CSB) |
| errorCount | int | 해당 회차 에러 건수 |
| lastStatus | Integer | `sam_api_call_log.last_status` (401 등, null 가능) |
| lastErrorBody | String | 마지막 에러 응답 본문(truncate) |
| authFailure | boolean | `lastStatus in (401, 403)` — 키 만료 추정 |
| occurredAt | LocalDateTime | 발생 시각 (KST, 전역 규칙 §1) |

### 4-2. 발행 지점 — `OpportunityCollectionScheduler`

`collectOpportunities()` 말미, 기존 `if (totalErrors > 0)` 블록을 확장:

- 발행 조건: `totalErrors > 0` **또는** `totalFetched == 0 && totalErrors == 0`이 아닌 인증 실패 감지
  - 구체적으로: 수집 직후 `SamApiCallLogRepository`에서 오늘(UTC) `search` 행을 조회,
    `last_status`가 401/403이면 `authFailure = true`로 발행
- 기존 `OpportunitiesCollectedEvent` 발행은 **그대로 유지**(성공 경로 무변경)

### 4-3. 알림 타입 신설 — `NotificationType.COLLECTION_FAILED`

- 템플릿 코드: 기존 `BID_COLLECTION_DONE` 재사용 (CR-018 선례 — 전용 템플릿은 후속 운영작업)
- 수신: `Member.Role.ADMIN` 전원
- 제목: `[Bidding Agency] ⚠️ 공고 수집 실패 (API 키 확인 필요)` — authFailure 시
  / `[Bidding Agency] ⚠️ 공고 수집 오류` — 그 외
- 본문 변수: `keyword`, `errorCount`, `lastStatus`, `reason`, `actionGuide`
  - authFailure 시 `actionGuide` = "SAM.gov > Account Details > Public API Keys 에서 키를 재발급받아
    서버 `.env`의 `SAM_GOV_API_KEY`를 교체 후 재기동하세요. (키는 90일 만료)"

### 4-4. 멱등키 — 하루 1통

`"COLLECTION_FAIL_" + keyword + "_" + LocalDate.now(KST)` 형식.
같은 날 4회 수집이 모두 실패해도 첫 회차 1통만 발송된다(BIZ-012 기존 로직이 그대로 차단).

### 4-5. 리스너 — `NotificationEventListener.onCollectionFailed`

`@Async @EventListener`로 신설. **0건 스킵 분기를 타지 않는다**(원인 #2 해소).

## 7. 비고 — 이번 사건에서 함께 확인된 것

- **백필 불필요**: 스케줄러 `daysBack = 30` 구조 덕에 키 교체 즉시 29건 소급 적재 완료(실측).
  단, 공백이 **30일을 넘으면 영구 손실**이므로 본 CR의 알림이 그 방어선이다.
- **시크릿 분리 완료**(커밋 `ec42e63`): 키가 compose 평문 → 서버 `.env` 주입으로 이전.
  키 교체 절차가 ".env 한 줄 + 재기동"으로 단순화되어, 알림을 받은 뒤 조치 비용도 낮아졌다.
- **git 히스토리 잔존 시크릿**: 과거 커밋에 옛 SAM 키·DB 비밀번호가 남아 있다.
  옛 SAM 키는 만료로 무해하나 **DB 비밀번호는 유효** — 별도 판단 필요(본 CR 범위 밖).
