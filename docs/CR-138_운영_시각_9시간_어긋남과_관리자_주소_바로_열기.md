## 2. 원인 (운영에서 직접 봄, 10/11 11:31~11:45)

### 2.1 운영 백엔드만 세계 표준시로 돈다

- 서버 시계는 서울(/etc/timezone Asia/Seoul), DB 도 서울(@@system_time_zone KST)이다. 백엔드 컨테이너만 `date` 가 UTC 이고 TZ 가 없으며 JAVA_TOOL_OPTIONS 에 user.timezone 이 없다
- docker-compose.prod.yml 에 TZ 가 없다. 개발용 docker/docker-compose.yml 14행의 TZ 는 MariaDB 컨테이너의 것이고 앱 설정이 아니다
- 앱의 시각 칸은 JVM 시간대 기준으로 드라이버에 넘어가고, 드라이버는 접속 설정(serverTimezone=Asia/Seoul)에 따라 서울 시각으로 바꿔 쓴다. 그래서 지금 시각으로 채운 칸(문의 접수, 가입, 처리 시각)은 DB 에 바르게 들어가고, 읽을 때 거꾸로 바뀌어 화면과 메일에 9시간 이르게 나온다

### 2.2 수집 때 만든 시각은 9시간 늦게 저장된다

- SAM 원본 마감은 서울 시각이다. sam.gov 공개 화면 API 로 본 원본: W91QVN27RA004 `2026-11-03T13:00:00+09:00`, W90VN627Q1CQ7 `2026-10-25T23:00:00+09:00`, W90VN926QA065 `2026-10-15T10:00:00+09:00`(responseTz Asia/Seoul)
- 수집의 날짜 읽기가 시간대 표시를 떼고 벽시계만 남긴다(OpportunityCollectorService.java:274). JVM 이 UTC 라 드라이버가 이 값을 세계 표준시로 보고 서울로 바꿔 쓰므로 9시간 늦게 저장된다. 날짜만 오는 게시일(00:00)은 09:00 으로 들어간다
- 운영 DB: W91QVN27RA004 22:00, W90VN627Q1CQ7 10/26 08:00, W90VN926QA065 19:00. 셋 다 원본보다 정확히 9시간 늦다
- 운영 공고 398건 중 게시일이 09:00 인 것이 386건(첫 생성 5/26 23:01 부터, 운영 수집분), 00:00 인 것이 9건(2~3월 맥에서 수집), 게시일이 비어 있는 것이 3건(6/21)이다. 공고 내용 갱신은 게시일과 마감을 함께 고쳐 쓰므로(Opportunity.updateContent) 게시일 09:00 이 "운영 UTC 상태에서 쓴 행" 의 표시가 된다
- 공고 목록(시장 화면 응답)은 저장 때 +9 와 읽을 때 -9 가 맞물려 지금은 `13:00+09:00` 으로 맞게 보인다. 시간대만 서울로 바꾸면 이 목록이 22:00 으로 틀어진다. 그래서 시간대 변경과 저장값 보정을 한 배포로 낸다

### 2.3 공고 상세 마감이 늘 "오전 09:00"

- 고객 공고 상세 응답의 마감은 날짜만 준다(OpportunityDto.java:35, yyyy-MM-dd). 상세 화면은 이를 시각까지 그리는데(BidDetailPage.tsx:78), 브라우저가 날짜만 있는 값을 세계 표준시 자정으로 읽어 서울에서는 늘 오전 09:00 이 된다. 시간대와 별개의 결함이다

### 2.4 관리자 주소를 바로 열면 고객 사이트가 뜬다

- http://woojinusbid.com/admin/inquiries, /admin/opportunities 를 열면 고객 포털 첫 파일(제목 WJbid.com, /assets/index-C4pWnTxt.js)이 온다. /admin/ 만 관리자 콘솔이 온다(10/11 11:31)

## 3. 확인한 것

### 3.1 9시간을 따로 보정하는 코드

- 백엔드: 9시간을 더하거나 빼는 코드는 없다. 서울 시간대를 명시한 곳(MarketRowAssembler, MarketDataService, MilitaryBaseService, NotificationEventListener, DocumentExpiryService, 스케줄러 3개)은 모두 "DB 값은 서울 벽시계" 를 전제한다. 지금 운영에서는 읽은 값이 UTC 라 이 전제가 깨져 있고, 바꾼 뒤 맞는다
- 화면: 9시간 보정은 없다. kstDate.ts, marketUtils.ts 는 서울 기준 "오늘 날짜" 만 구한다. 시각은 응답 문자열을 브라우저 시각으로 그린다
- 맞물려 상쇄되던 곳은 공고 게시일과 마감 둘이다(2.2). 보정 마이그레이션으로 푼다

### 3.2 정해진 시각에 도는 작업

| 순번 | 작업 | 설정 | 시간대를 바꾼 뒤 |
|---|---|---|---|
| 1 | SAM 공고 수집 06, 12, 18, 23시 | cron, zone Asia/Seoul (OpportunityCollectionScheduler.java:47) | 그대로 |
| 2 | 마감 임박 알림 09시 | cron, zone Asia/Seoul (DeadlineAlertScheduler.java:29) | 그대로 |
| 3 | 서류 만료 메일 09시 | cron, zone Asia/Seoul (DocumentExpiryScheduler.java:19) | 그대로 |
| 4 | 분석 멈춤 정리 10분마다 | 간격 (NoticeStuckCleanupScheduler.java:38) | 그대로 |

- 이 넷 밖에 정해진 시각에 도는 작업(@Scheduled, TaskScheduler, 예약 실행기)은 없다. 실행 시각은 이미 서울 기준이라 옮겨지지 않는다
- 작업 안의 비교(마감까지 남은 날, 멈춤 판정)는 읽은 값과 지금 시각이 함께 서울로 바뀌어 결과가 같다. 다만 공고 마감은 저장값이 +9 라 보정과 함께 나가야 같다

### 3.3 시간대를 바꾸면 뜻이 바뀌는 곳

- SAM 호출 기록의 마지막 호출 시각(SamQuotaLogger.java:75)을 세계 표준시 벽시계로 넣는다. 지금은 드라이버가 서울로 바꿔 써서 서울 값이고, 바꾼 뒤에는 9시간 이른 값이 들어간다. 앱 시계로 고친다. 호출 일자(SAM 쿼터의 UTC 날짜)는 따로 UTC 시계를 써서 영향 없다
- 수집 기간의 끝날(오늘)이 UTC 날짜에서 서울 날짜로 바뀐다. 서울 날짜는 늘 같거나 하루 뒤라 덜 받는 공고는 없다. 시작날은 DB 최근 게시일 하루 전이라 그대로다
- 로그 시각이 서울로 바뀐다
- 로그인 토큰 만료, Redis 만료, DB 기본값 NOW() 는 순간값이라 영향 없다

### 3.4 저장값 (로컬에서 본다)

- 시각 칸: JVM 이 서울이 되면 드라이버 변환이 없어지고, 지금 시각으로 넣은 값은 지금과 같은 값으로 저장된다. 로컬에서 JVM 을 UTC 와 서울로 각각 띄워 같은 동작의 저장값이 같은지 본다
- 날짜 칸(서류 만료일 등): 같은 방법으로 하루 밀림이 없는지 본다
