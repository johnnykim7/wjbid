# CR-125 — 회사 공통 서류함 (Member 종속 보관함 + 제안서 슬롯 자동채움)

> 상태: **설계** (2026-06-30) · 규모: **중규모** (신규 엔티티·테이블·API·화면 실연동 + 자동매칭)
> 원칙: CLAUDE.md "설계 우선" — 본 문서 + T3-1/T3-2/T3-3/CR이력 갱신 후 코드 착수

---

## 1. 배경 / 목표

- **문제의식(사용자)**: 사업자등록증·CAGE 증빙 같은 **회사 공통 서류는 매 공고마다 다시 올리기 귀찮다.** 한 번 넣어두고 재사용하고 싶다.
- **현황 실측(2026-06-30)**:
  - 현 `/documents` 화면 [DocumentsPage.tsx](../frontend/customer-portal/src/pages/DocumentsPage.tsx) = `DUMMY_SLOTS` 하드코딩 + **BE 미연동 껍데기**(업로드/교체/삭제 버튼 다 죽음, 하단에 "시연용 더미" 자인).
  - `ClientDocument` [ClientDocument.java](../backend/src/main/java/com/biddingagency/domain/bid/entity/ClientDocument.java) = **공고/입찰 종속**(`@ManyToOne BidRequest nullable=false`). 엔드포인트 `/bid-requests/{bidRequestId}/client-documents`. 즉 "이 공고에 제출할 서류"이지 회사 공통 보관함이 **아님**.
  - **공통 서류함(member 종속)은 BE에 아예 없음** → 신규 엔티티 필요.
  - 제출 슬롯 매칭은 CR-010 `RequiredDocumentSlotController` / `ComplianceService.uploadToSlot` / `RequirementFulfillmentMap`(`client_document_id` FK 보유)에 존재.
  - 스토리지는 `StorageService` 추상화 + `LocalFileStorageService`(로컬 디스크 1차 구현). MinIO는 향후 `S3StorageService` 교체 지점. (메모리 "MinIO 저장"은 추상화 의미 — 실코드는 StorageService 사용)

## 2. 범위 (확정 정책)

**1+2단계 둘 다.**

### 1단계 — 회사 공통 서류함 (member 종속)
- 신규 엔티티 `MemberDocument` — member 종속, 카테고리, StorageService 저장.
- 업로드 / 목록 / 교체 / 삭제 API + `/documents` 화면 실연동(더미 제거).

### 2단계 — 제안서 작성 시 공통서류 자동 채움
- 공고 요구 슬롯(`RequiredDocumentSlot`)에 **서류함의 같은 카테고리 서류를 자동 매칭**("서류함 거 그대로 쓰기").
- 자동매칭 = 서류함 `MemberDocument` → 슬롯용 `ClientDocument` 복사(원본 보존) + `RequirementFulfillmentMap.fulfillWithClientDocument`.

## 3. 카테고리 정책 (확정)

**고정 + 자유 병행.**
- 고정 카테고리(자동매칭 대상): `BUSINESS_REGISTRATION`(사업자등록증) · `CAGE`(CAGE 증빙) · `COMPANY_PROFILE`(회사소개서) · `FINANCIAL_STATEMENT`(재무제표) · `SAM_REGISTRATION`(SAM 등록증) · `PAST_PERFORMANCE`(과거 수행실적).
- `OTHER`(기타) — 자유 업로드 허용. **자동매칭은 고정 카테고리만.**

## 4. 데이터 모델 (T3-1 반영)

### 신규 테이블 `member_documents` (V39)
| 컬럼 | 타입 | 제약 | 설명 |
|------|------|------|------|
| id | BINARY(16) | PK | BaseEntity |
| member_id | BINARY(16) | FK members, NOT NULL | 소유 회원 |
| category | VARCHAR(40) | NOT NULL | DocumentCategory enum |
| file_name | VARCHAR(500) | NOT NULL | 원본 파일명 |
| file_size | BIGINT | NOT NULL | 바이트 |
| content_type | VARCHAR(100) | NOT NULL | MIME |
| storage_url | TEXT | NOT NULL | StorageService 상대경로 |
| display_name | VARCHAR(255) | NULL | 문서제목(고정=카테고리 한글명 자동, 기타=사용자 입력 필수) |
| description | TEXT | NULL | 설명 메모(기타 전용 — 고정은 미사용) |
| created_at / updated_at | DATETIME | | BaseEntity |

- **인덱스**: `idx_member_documents_member(member_id)`, `idx_member_documents_member_category(member_id, category)`.
- **고정 카테고리 1슬롯 = 1서류 원칙**: 같은 member+고정카테고리 재업로드 = 기존 레코드 교체(파일 삭제 후 갱신). `OTHER`는 다건 허용.

### `DocumentCategory` enum (신규, domain/member 또는 common)
`BUSINESS_REGISTRATION, CAGE, COMPANY_PROFILE, FINANCIAL_STATEMENT, SAM_REGISTRATION, PAST_PERFORMANCE, OTHER` — 각 `displayName`(한글), `fixed`(boolean) 보유.

### 기존 모델 무변경
- `ClientDocument`·`RequirementFulfillmentMap`·`member` 테이블 변경 없음. 2단계는 기존 `client_document_id` 매핑 경로 재사용.

## 5. API 설계 (T3-2 반영)

### 1단계 — 서류함 CRUD (`/member-documents`, 인증=본인 member)
| 메서드 | 경로 | 설명 |
|--------|------|------|
| GET | `/member-documents` | 내 서류함 목록(카테고리별) + 고정 카테고리 슬롯 메타 |
| POST | `/member-documents` (multipart) | 업로드 — `file`, `category`, `displayName?`, `description?`(기타 전용) |
| PUT | `/member-documents/{id}` (multipart) | 교체(파일 재업로드) |
| DELETE | `/member-documents/{id}` | 삭제(StorageService 파일도 삭제) |

- 응답 DTO `MemberDocumentDto`(LAZY 폭발 방지, ClientDocumentDto 패턴) + `MemberDocumentVaultResponse`(고정슬롯 + 기타 목록 한 번에).
- member 식별 = `@AuthenticationPrincipal CustomUserDetails.getMember()`. 타 member 문서 접근 차단(소유 검증).

### 2단계 — 슬롯 자동채움 (CR-010 슬롯 컨트롤러에 추가)
| 메서드 | 경로 | 설명 |
|--------|------|------|
| POST | `/bid-requests/{bidRequestId}/required-document-slots/auto-fill` | 서류함에서 같은 카테고리 서류를 미충족 슬롯에 일괄 자동매칭 |

- 동작: 미충족(`PENDING/MISSING`) 슬롯들의 `category`를 서류함 고정 카테고리와 매칭 → 해당 `MemberDocument`를 `ClientDocument`로 복사(StorageService 파일 복제 or storage_url 재사용 결정) → `fulfillWithClientDocument`.
- 응답 = 갱신된 `RequiredDocumentSlotsResponse`(기존 GET 슬롯과 동형) + 자동채움 건수.
- 개별 슬롯 단위 채움도 옵션: `POST .../{requirementItemId}/auto-fill`(서류함에서 1건). 1차는 일괄만, 개별은 화면 요구 시.

## 6. 화면 구조 (T3-3 반영)

### 6-1. 서류함 `/documents` (DocumentsPage 실연동)
- 더미 제거. `getMemberDocumentVault()` 로드 → 고정 카테고리 6슬롯 카드 + "기타 서류" 목록.
- **고정 카드**(사업자등록증·회사소개서 등): 제목 고정. **파일만** 선택해서 업로드/교체/삭제. 별도 입력 모달 없음(파일 피커만). 설명 입력 없음.
- **기타 서류(비고정)**: "기타 서류 추가" 버튼 → **등록 모달**:
  - 문서제목 (`displayName`, 필수)
  - 파일 첨부 (`file`, 필수)
  - 설명 (`description`, 선택 — 짧은 메모)
  - → `category=OTHER` 고정으로 POST. 목록에 카드/행으로 누적(다건 허용), 행별 교체·삭제.
- 요약 StatCard(보관 N건 / 고정 미등록 N건)는 실데이터 기반.

### 6-2. 제안서/입찰 상세 슬롯 화면 (자동채움 버튼)
- 기존 "필요 서류 체크리스트"(BidDetailPage / 슬롯 화면)에 **"서류함에서 자동 채우기"** 버튼 추가.
- 클릭 → `auto-fill` 호출 → 슬롯 목록 갱신 + "N건 자동 채움" 토스트. 서류함에 없는 카테고리는 미충족 유지(수동 업로드 안내).

## 7. FSM / 이벤트 영향

- **FSM 무변경**: 서류함은 member 종속 보관소로 상태기계 밖. 자동채움은 기존 슬롯 충족 경로(`DOCS_PENDING → DOCS_RECEIVED` 사전조건, BIZ-015)를 그대로 탐. 새 전이 없음.
- **이벤트**: 신규 도메인 이벤트 불필요(1차). 자동채움은 기존 fulfillment 갱신만.

## 8. 비즈니스 규칙 (T1-3 반영)

- **BIZ-125-1**: 서류함 문서는 **본인 member만** 조회/수정/삭제(소유 검증 필수).
- **BIZ-125-2**: 고정 카테고리는 member당 최대 1건(재업로드=교체). `OTHER`는 다건.
- **BIZ-125-3**: 자동매칭은 고정 카테고리만. 슬롯↔서류함 카테고리 동일성으로 매칭.
- **BIZ-125-4**: 자동채움은 **미충족 슬롯만** 대상. 이미 충족된 슬롯은 덮어쓰지 않음(고객 수동 매핑 보호).
- BIZ-011(50MB 제한)·StorageService path traversal 방지 기존 규칙 승계.

## 9. 미결 / 결정 필요 (구현 중 확정)

1. **자동채움 시 파일 복제 vs storage_url 공유**: `ClientDocument`를 새로 만들 때 StorageService 파일을 실제 복제할지(독립성) vs MemberDocument storage_url을 그대로 가리킬지(중복 절약). → 슬롯 삭제 시 원본 보존 안전을 위해 **복제** 권장(1차).
2. 개별 슬롯 자동채움 UI 필요 여부(1차는 일괄 버튼만).

## 10. 규모 / 절차

- **규모**: 중규모. 신규 테이블 1 / 신규 API 5 / 화면 2(서류함 실연동 + 슬롯 자동채움 버튼). 데이터모델 추가(member_documents), 기존 모델 무변경, FSM·이벤트 무변경.
- **절차**: 본 설계서 + T3-1/T3-2/T3-3 + CR이력 갱신 → 설계 커밋 → 1단계 구현(엔티티/V39/API/화면) → 2단계 구현(auto-fill) → 검증.
- **FlowGuard**: 매개 원칙 대상(신규 기능). 등록은 사용자 결정 보류(메모리 기재대로).
