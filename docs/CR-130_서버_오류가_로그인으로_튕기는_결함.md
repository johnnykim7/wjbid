## 2. 원인 (2026-10-10 21:35 조사)

| 순번 | 자리 | 지금 동작 |
|------|------|-----------|
| 1 | 서버 안 오류 처리 | 처리하지 못한 예외, 없는 주소, 프레임워크가 내는 400 은 서버 안에서 오류 경로(/error)로 다시 들어간다. 이 재요청에서는 로그인 정보를 읽는 필터(JwtAuthenticationFilter, OncePerRequestFilter)가 돌지 않아 미로그인으로 취급된다 |
| 2 | 보안 설정 config/SecurityConfig.java | 허용 목록에 오류 재요청이 없어 마지막 줄 "나머지는 로그인 필요"에 걸리고 미인증 응답 401 을 낸다. 공개 경로(요금, 공고)의 요청도 같다 |
| 3 | 고객 포털 공통 처리 api/client.ts | 401 을 받으면 갱신 토큰으로 새 토큰을 받아 같은 요청을 다시 보낸다. 다시 보낸 요청도 401 이면 또 갱신하고 또 보낸다(횟수 제한 없음). 갱신이 실패하면 저장값을 지우고 로그인 화면으로 보낸다 |

- 운영 실측(21:35): 공개 경로의 없는 주소 `GET /api/opportunities/0/__nope__/x` 가 404 가 아니라 401. 같은 서버 `GET /api/health` 는 200
- 영향: 오류 경로를 거치는 응답이 모두 401 로 보인다. 회원가입 화면이 서버 안내 문구(response.data.message)를 보여주도록 되어 있으나 지금은 그 문구가 오지 않는다

## 3. 고치는 방향

1. 보안 설정: 오류 재요청(ERROR dispatch)을 허용한다. 원래 요청에서 이미 권한 검사를 거쳤으므로 오류 응답을 쓰는 단계만 연다. 주소 /error 를 밖에서 직접 부르는 요청은 지금처럼 로그인이 필요하다
2. 내부 오류 문구: `server.error.include-message: always` 라서 오류 경로가 열리면 처리하지 못한 예외의 문구가 응답에 실린다(로컬 실측: 요금 표가 없을 때 500 응답 message 에 조회 쿼리와 표 이름 `bidding_agency.system_settings` 가 그대로 나옴). DB 접근 오류처럼 내부 구조가 담기는 문구는 서버 기록에만 남기고 응답에는 일반 안내만 준다(사용자 10/10 22:00 승인, 범위 1번)
3. 고객 포털: 401 뒤 갱신해서 다시 보내는 것은 요청마다 한 번만 한다

## 4. 완료 기준

- 로컬: 공개 경로의 서버 오류는 500, 없는 주소는 404. 미로그인으로 보호 경로를 부르면 401, 권한이 모자라면 403 그대로. 고객 화면에서 서버 오류가 나도 로그인 화면으로 가지 않고 그 화면의 실패 안내가 나온다
- 운영 배포(백엔드, 고객 포털) 뒤 같은 확인
