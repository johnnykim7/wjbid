# 쟁점지 - 제안서 작성 개편

## 정할 것
제안서 작성을 어떻게 다시 짤 것인가. 지금 흐름에서 버릴 것과 살릴 것은 무엇이고, sam-proposal 스킬 7단계를 어느 자리에 어떤 꼴로 넣으며, 어떤 순서로 들일 것인가(계획만 있는 CR-171 ~ 175 포함).

## 배경
- 11/5 상용에서 낙찰 공고 W90VN825R0006(캠프 케이시와 용산 잔디 관리, 녹화창조 31억 낙찰)으로 서류 등록, 작성 요청, AI 제안서 작성을 돌려 실제 제출본과 견줬다. 큰 차이가 다섯 가지 나왔다.
- 그중 우리 결함 셋(가격 항목, 공고 내용 전달, 정부 양식)은 CR-189 로 고쳐 11/8 상용에 올렸다. 같은 건 재시험은 하지 않았다.
- 제안서 작성은 스킬 지침 12편 중 4편만 쓴다. 수주 전략, 요약문, 전체 리뷰는 10/24 에 CR-171 ~ 175 로 번호만 따 두었다.
- 사람 11/8 08:39: "우리가 만든것에서 버릴것은 버리고 차용할것은 차용하고 전면 개편이 가능할까요? 저 스킬을 잘 활용해서"

## 전제 - 다투지 않는 것
- 단계 순서는 우리 서버가 정하고, 각 단계 안에서는 AI 가 도구를 스스로 불러 일한다 (사람 11/8 08:38 "순서는 당연히 우리가 정하는데")
- 스킬은 원본 파일 구성과 문장을 그대로 두고, 한국 조달에만 맞는 줄만 고쳐 쓴다 (사람 10/16 07:01 "스킬파일의 원본을 최대한 활용할수있도록")
- 수주 전략은 관리자가 승인한 뒤에 본문을 쓴다 (사람 10/24 20:56, CR-171)
- 공고 사실은 공고 분석 결과에서만, 회사 사실은 고객 서류와 회사 정보에서만 쓴다 (BIZ-101, CR-189)
- 실행은 Aimbase 작업 흐름이고, 작업 흐름 정의는 우리 레포 `docs/workflows/` 에 둔다

## 아는 사실

### 지금 흐름
- 공고 분석은 7단계다. 공고 가져오기, 설명 쓰기, 첨부 받기, 파일별 사실 뽑기, 검증과 빠진 것 찾기, 요구사항 매트릭스 만들기, 저장 (출처: docs/workflows/opportunity-analysis.steps.v3.json). 시험 공고에서 공고 사실 85건, 매트릭스 94줄이 나왔다 (상용 조회 11/6)
- 고객 서류 읽기와 입찰 분석은 따로 된 작업 흐름이다 (출처: docs/workflows/client-document-read.steps.json, bid-analysis.steps.json, CR-170)
- 제안서는 서버가 목차 설계를 1번, 절마다 작성을 1번(다시 쓰기 포함), 절마다 충실성 검증을 부른다 (출처: backend/.../bid/service/AIWorkflowService.java 206, 254, 290, 312줄)
- 각 단계는 AI 에이전트 호출 1번이다. 도구를 몇 번 부를지는 정하지 않고 시간만 묶는다. 목차 설계 10분, 절 작성 30분, 검증 10분 (출처: docs/workflows/proposal-design, proposal-write-section, proposal-verify-fidelity 의 timeout_ms)
- 제안서는 장, 절, 블록으로 DB 에 저장되고 관리자 콘솔 절 트리에서 본다 (CR-027, CR-030). 내보내기는 PDF 하나다 (출처: backend/.../controller/BidDocumentController.java 108줄)
- 문서 구성은 공고 평가 항목 트리가 정한다(CR-180). CR-189 부터 정부 양식 문서를 맨 끝에 붙인다
- 절 작성 지시문은 한국어 초안을 쓰게 한다 (출처: docs/workflows/proposal-write-section.steps.json 14줄). 영문 변환은 기능요구사항의 향후 기능 표에만 있다 (출처: docs/AI-SDLC/T1-1_기능요구사항_명세서.md 1298줄)

### 스킬 (sam-proposal)
- 묶음은 SKILL.md, 작성 지침 12편, 도구 3개(HWP 변환, 커버리지 검사, 도식 캡처), 도식 견본 7개, 서식 견본 8개다. 운영 Aimbase 에 올라가 있다 (출처: docs/skills/sam-proposal/, 상용 Aimbase 조회 11/8)
- 7단계는 RFP 분석, Bid/No-Bid, 전략 수립, 목차와 스토리, 섹션 기획, 본문 작성, 리뷰다. 척추는 1단계에서 요구사항마다 ID 를 매기고 그 ID 가 목차, 섹션 기획, 본문, 커버리지 검증까지 관통하는 컴플라이언스 매트릭스다 (출처: docs/skills/sam-proposal/SKILL.md 19 ~ 30줄)
- 지금 쓰는 지침은 목차 설계에 04, 05, 00, 절 작성에 06, 00, 검증에 07 이다. 01, 02, 03, 08 ~ 11, 도구, 견본은 제안서 작성에 쓰지 않는다 (출처: docs/workflows/proposal-*.steps.json 의 skills 칸)
- CR-171 ~ 175 는 10/24 에 번호를 땄고 모두 상태 계획이다. 171 수주 전략과 관리자 승인 관문, 172 목차와 절 기획서 저장과 표시, 173 본문, 요약문, 도식, 장 표지, 워드 표준 서식, 174 제안서 전체 리뷰(7기준 평가, 모의 채점), 175 회사소개서, 사전 의향조사 회신, 콜드메일 (출처: docs/CR/CR_변경_이력.md 1351 ~ 1385줄)
- 스킬과 Aimbase 작업 흐름의 관계는 흐름도로 그려 두었다 (출처: docs/기록/WJbid_AI_작업흐름_20261106.html)

### 평가 방식
- 이 공고는 LPTA 다. 기술 요소는 점수 없이 합격과 불합격으로만 보고, 하나라도 불합격이면 제안 전체가 부적격이다. 요소 A 기술(소계수 1 ~ 5), B 과거 실적, C 가격 (출처: 상용 공고 분석 요약, 자료/원자료/notice-run2.json)
- 상용에서 분석을 마친 공고 55건 중 평가 항목 트리가 있는 것은 11건이다. 그중 LPTA 5건, 최고 가치 절충 5건, 미상 1건 (상용 조회 11/8)

## 모르는 사실
- CR-189 뒤 상용에서 가격 항목과 정부 양식이 실제로 나오는지 (재시험 안 함)
- 회사 정보를 녹화창조 것으로 채우면 입찰 분석 판정과 작성 결과가 달라지는지
- 실제 제출본의 장마다 사람이 얼마나 걸려 썼는지, 어느 부분이 회사 자료를 옮긴 것인지
- 이 건의 실제 평가 기록. LPTA 라 기술은 합격 여부만 보고 가격으로 갈린다는 것은 공고 기준이다
- 스킬 단계를 늘리면 한 건 시간과 비용이 얼마나 느는지
- 영문으로 바로 쓰는 것과 한국어로 쓴 뒤 옮기는 것의 품질 차이
- 다른 업종(공사, 물품) 공고에서도 같은 차이가 나는지. 견준 낙찰 건은 1건뿐이다
- 상용 공고 55건 중 44건은 평가 항목 트리가 없어 평가 방식을 구조로 알 수 없다

## 후보 안
- 안 A: 지금 흐름(목차 설계, 절 작성, 충실성 검증)을 그대로 두고, 스킬의 빠진 단계를 CR-171 ~ 175 순서대로 앞뒤에 붙인다
- 안 B: 스킬 7단계를 작업 흐름 단계로 그대로 옮겨 제안서 작성을 다시 짠다. 지금 것 중 공고 분석, 요구사항 매트릭스, 장 절 블록 저장, 충실성 검증은 스킬 단계 안의 부품으로 쓴다
- 안 C: 제출 문서의 꼴에 따라 흐름을 나눈다. 서술형 계획서(관리 계획, 장비 계획 같은 것)는 스킬 단계를 거치고, 증빙 묶음형(등록, 실적, 인력), 가격, 정부 양식은 각각 짧은 흐름으로 만든다
- 참가자는 새 안을 낼 수 있다
